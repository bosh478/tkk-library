## ⚠️ 首次扫描与末次扫描铁律（v31 新增）

**问题根因**：第一次只扫描了"当时存在的文件"，后来新增的文件永远发现不了。

**铁律**：ingest 操作分两个时间点必须扫描源目录：
1. **首次扫描**（处理前）：
   - 源目录为 `sources/` 时：`ls sources/xxx/*.md | wc -l`
   - 源目录为 `Clippings/` 时：`ls D:/AI\ agent/tkk-library/Clippings/*.md | wc -l`
   → 记录为基准数量
2. **末次扫描**（处理后）：
   - 源目录为 `sources/` 时：`ls sources/xxx/*.md | wc -l`
   - 源目录为 `Clippings/` 时：`ls D:/AI\ agent/tkk-library/Clippings/*.md | wc -l`
   → 再次执行，对比是否一致

**末次扫描的作用**：
- 如果两次数量一致 → 处理期间无新增文件，验证通过
- 如果两次数量不一致 → 发现了处理期间新增的文件，必须继续处理遗漏的文件
- **禁止跳过末次扫描**：即使"确信没有新增文件"也必须执行，这是验证不是可选步骤

**执行顺序**：
```
首次扫描 → 记录: "源目录: X个文件"
    ↓
处理文件（阶段一至五）
    ↓
末次扫描 → 对比: "源目录: X个文件" vs "处理: X个文件"
    ↓
数量一致 → 验证通过，输出"验证结果：源目录X个，处理X个，全部完成"
数量不一致 → 主会话接管，继续处理遗漏文件
```

## 阶段一：源文件清单分析 + 去重检查

### @步骤

1. `ls sources/xxx/*.md | wc -l` 统计总数
2. 识别文件类型分布（律师指引/法律法规/司法解释/案例）
3. 识别命名模式（日期格式、前缀规律）
4. **@强制：检查同系列已有 wiki 文件的命名前缀**
   ```bash
   # 批量处理前，先检查同系列已有文件的命名前缀，沿用而非另起炉灶
   ls wiki/summaries/ | grep -E "关键词" | head -3  # 如 Court_/SPP_GuideCase_/LawyerGuide_
   ```
   **@验证**：执行以下命令确认新文件使用了与已有文件一致的前缀：
   ```bash
   ls wiki/summaries/ | grep -E "匹配前缀" | head -3
   # 输出应包含与源文件同系列的所有文件，无新增不一致前缀
   ```
5. 识别超大文件（>5000行）和普通文件

### @首次扫描必须记录（铁律）

**阶段一执行前**，必须在 log.md 写入首次扫描记录：

```
## [YYYY-MM-DD] 首次扫描 | sources/xxx/
- 基准数量: X 个文件
```

**无首次扫描记录 → 阶段一未完成，不得进入阶段二**

### @分组规划

| 规模 | 策略 |
|------|------|
| < 20个 | 单 Agent 串行 |
| 20-100个 | 按法律部门分组，≤30个/组 |
| > 100个 | 分层处理，每组≤30个且≤6000行 |
| 超大文件（>5000行） | **单独处理，见下方专项规则** |

### @超大文件专项处理规则（>5000行）

1. **识别文件结构**：
   ```bash
   grep -n "^# " sources/超大型文件.md | wc -l   # 统计章节数
   grep -n "^## " sources/超大型文件.md | wc -l  # 统计子章节数
   ```
2. **判断类型**：
   - **合订本**（如司法解释全书含189个独立解释）→ 按 `# 标题` 拆分为多个 entity，每批处理 10-20 个章节
   - **单一本**（如某罪的完整释义）→ 按 `## 标题` 拆分为多个 section，分批处理
3. **批次规划**：每批处理不超过 20 个 `# 章节`，完成后验证（数量核验 + 内容抽检），再处理下一批
4. **提取规则**：每个 `# 标题` 对应一个 `entity_*.md` 文件，逐条提取条款内容
5. **目标目录**：`wiki/entities/`（司法解释全书属于 entity 类）

### @去重检测
```bash
# 检测重复后缀 (1)、(2) 等
ls sources/xxx/*.md | grep -E '\ \([0-9]+\)$'
```

### @Layered Confidence Rejection（v39 新增）

内容提取时按置信度分层拦截，不同级别的内容走不同处理路径。

| 置信度 | 来源 | 处理方式 |
|--------|------|----------|
| 高 | 原文直接引用（逐字提取） | 直接写入 wiki |
| 中 | 原文转述（保留核心语义） | 写入 + 标注 〔存疑〕 |
| 低 | 个人解读/跨资料关联 | 写入 + 标注 〔待核实〕+ 同步 log.md |
| 极低 | 高度不确定/逻辑跳跃 | **拒绝写入 wiki**，只存入 log.md 待验证 |

**⚠️ 极低置信内容不得混入 wiki**：如果某条内容属于"高度不确定"或"逻辑跳跃"，即使很有价值也必须暂存 log.md，待验证后再决定是否写入 wiki。

### @核心原则：分层提取，不是整文件处理

| 内容类型 | 处理单元 | 方式 |
|----------|----------|------|
| 法规/法条 | 逐条 | 每条独立释义 |
| 司法解释 | 逐条+逐款 | 解释条款是独立单元 |
| 案例分析 | 逐案 | 每案独立要旨 |
| 书籍章节 | 逐节/逐章 | 不能整本一起处理 |

**⚠️ 全部章节原则**：必须提取全部章节，不能只处理目录

### @差异驱动写入（v34 新增）

每份法律资料 ingest 时，必须在正文中包含：

```markdown
## 相比同类旧资料的核心差异
```

具体要求：

| 内容类型 | 差异提取重点 |
|----------|------------|
| 司法解释 | 必须提取"相对旧解释的具体变更点"（数额/主体/行为模式/程序要件），对照表格呈现 |
| 案例分析 | 必须提取"裁判要旨相比同类案件的差异化要点" |
| 法律法规修正 | 必须提取"相比修正前的主要变化点" |

示例（司法解释）：
```markdown
## 相比旧解释的核心变更

| 变更维度 | 旧解释（法释〔2016〕9号） | 新解释（法释〔2026〕6号二） |
|----------|--------------------------|----------------------------|
| 受贿罪数额标准 | 3万/20万/300万 | 维持不变 |
| 谋取利益要件 | 兜底条款 | 明确三种具体情形 |
```

### @知识节点原子化提取（Zettelkasten v52 新增）

每个知识点必须独立提取，包含行号脚注和知识关联：

**知识点原子化标准**（满足任一即为独立节点）：
- 独立规则（构成要件、判断标准、程序要求）
- 独立案例（裁判要旨、典型意义）
- 独立定义（法律概念定义）
- 独立数额/日期（量刑标准、生效日期）
- 差异化要点（旧资料对比）

**提取步骤**：
1. 扫描源文件，识别所有独立知识点
2. 对每个知识点：
   - 提取原文内容（高置信度，逐字复制）
   - 用 grep 定位关键词所在行号
   - 标注 `① 来源：行XXX[^fnN]`
   - 在 frontmatter 的 `line-refs` 字段记录：`"源文件.md": [行号1, 行号2]`
   - 在 frontmatter 的 `related` 字段添加 wikilink 关联
3. 知识缺口检查：发现孤立节点或链接断裂时使用 `> [!gap]+` callout 标注

**行号脚注格式**：
```markdown
## 知识点：名称
（原子内容）

① 来源：行13637[^fn1]

---

## 引用

[^fn1]: 源文件名.md#L13637
```

**多行引用**：
```markdown
① 来源：行13637-13639[^fn1]

[^fn1]: 源文件名.md#L13637#L13639
```

### @相关主题自动发现（深度链接增强 v50）

内容提取完成后，执行以下深度链接流程：

#### 步骤1：标签匹配
```bash
# 扫描当前页面的 tags
grep "^tags:" wiki/xxx.md | sed 's/tags: \[//' | sed 's/\]//' | tr ',' '\n'
# 匹配相同 tags 的其他页面
for tag in <当前页面tags>; do
  grep -r "tags:.*$tag" wiki/ --include="*.md" | grep -v "当前页面" | head -5
done
```

#### 步骤2：层级链接（hierarchyLevel）
- 当前页面的 hierarchyLevel 对应的上位法链接（层级-1）
- 当前页面的 hierarchyLevel 对应的下位法链接（层级+1）
- entity 类型必须链接上位法（如有）

#### 步骤3：差异驱动链接
```markdown
## 相比同类旧资料的核心差异
```
- 司法解释：对照旧解释提取具体变更点（数额标准/适用范围/构成要件）
- 案例分析：提取裁判要旨相比同类案件的差异化要点
- **触发条件**：发现"差异"时才写入，无差异则标注"无显著差异"

#### 步骤4：related 字段更新
更新 frontmatter 的 related 字段，包含：
1. 同标签页面（≥1个）
2. 上位法/下位法链接（如有）
3. 差异对比结论（无差异则标注"无显著差异"）

**验证命令**：
```bash
grep "^related:" wiki/xxx.md  # 必须非空
```

**回溯修复脚本**：
```bash
python retro_fix_related.py wiki/summaries/  # 扫描并建议
python retro_fix_related.py --apply wiki/summaries/  # 应用修改
```

## 阶段三：数量核验 + 内容质量检查

### @七步骤必须全部执行（与 lint-workflow.md 一致）

1. **脚本精确比对**：找出未处理的 source 文件
2. **文件大小检查**：< 3KB 可能为空（小型法律除外）
3. **内容抽检**：正文 > 500 字符、前100字符非空
4. **占位符扫描**：`待补充`、`见原文`、`（略）`
5. **量刑档次核对**：三档/四档不得遗漏（见下方核验方法）
6. **分类统计验证**：各目录文件数与预期一致
7. **源文件完整性验证**：wiki 页面的 source 字段指向的源文件是否存在

### @量刑档次核验标准方法

```
核验步骤：
1. 识别罪名/司法解释名称
2. 搜索量刑关键词："三年"+"七年"+"十年"+"无期"+"死刑"出现次数
3. 对照典型罪名档位：
   - 贪污罪/受贿罪：3档（3年↓/3-10年/10年↑或死刑）
   - 盗窃罪：3档（1000元↓/1000-50000元/50000元↑）
   - 诈骗罪：3档（数额较大/巨大/特别巨大）
4. 确认每档都有对应提取内容
5. 如果档数不符 → 标记具体缺失档位，补充提取
```

**占位符扫描**：搜索以下模式，有则必须返工：
```
待补充、見原文、（略）、TODO、占位符
```

## 阶段四：整合入库（6步骤）

**⚠️ qmd embed 不等于整合入库！**

| 步骤 | 内容 | 验证方法 |
|------|------|----------|
| 1 | 交叉链接：更新 related 字段 | `grep "^related:" wiki/xxx.md` 确认非空 |
| 2 | 更新 index.md：对用分类添加条目 | `grep "页面名" index.md` 确认存在 |
| 3 | 更新 sources/INDEX.md：追加源文件索引 | `grep "文件名" sources/INDEX.md` 确认存在 |
| 4 | 更新 log.md：记录 ingest 事件（含完整原始文件名清单） | `grep "文件名" log.md` 确认存在 |

| 6 | qmd update：将新 wiki 文件加入索引 | `qmd status` 确认文档数增加 |
| 7 | qmd embed：增量生成向量 | 向量库更新确认 |

#### 自动归档

# 执行归档

- 需要确保 wiki 页面已正确创建（source 字段已指向源文件）
- 需要确保 sources/INDEX.md 已更新（源文件路径已变更）

**@移动规则**：
- 源文件移动到 `sources/网络文章/` 目录
- 保留原始文件名不变
- 移动后 Clippings/ 目录清空
- 同步更新 wiki 摘要页的 source 路径（`Clippings/` → `sources/网络文章/`）

**⚠️ 注意**：此规则仅适用于 vault 根目录下的 `Clippings/` 文件夹，其他来源目录的源文件**不得移动**。

## 阶段五：完成报告

### @阶段五前置检查（铁律）

**报告输出前必须执行以下检查**：

1. **检查首次扫描记录**：log.md 中是否存在对应日期的首次扫描记录
   - 如果首次扫描记录缺失 → 补充记录后再输出报告

2. **检查末次扫描记录**：末次扫描结果是否已记录在 log.md
   - 如果末次扫描未执行 → 执行后再输出报告

### @报告必须包含的内容

1. 数量汇总（基于脚本验证）
2. 提及异常（如某文件规模偏小）
3. log.md 记录（**必须包含完整原始文件名清单**）
4. **首次扫描基准数量**（从 log.md 读取）
5. **末次扫描对比结果**（数量是否一致）
6. **报告用户：完成情况 + 还需要处理什么**

**⚠️ 末次扫描未执行 → 报告不完整，不得结束**

## 批量 Ingest 执行规范（经验固化）

> 批量处理（≥10个文件）时，在阶段一至五基础上，额外遵循以下规则。

### @并行 Agent 策略（阶段二执行）

| 问题 | 根因 | 解决方案 |
|------|------|----------|
| Agent 报告"处理 3-5 个" | 上下文限制 | **立即用脚本验证** |
| Agent 报告"全部完成" | 未检查实际文件 | **精确比对** source vs target |
| 数量对不上 | 覆盖/遗漏 | **主会话接管处理遗漏** |
| 置信度未标注 | 遗漏 | 补充标注 |
| 章节遗漏 | 提取不完整 | 补充提取 |

### @Phase门硬性检查（阶段一完成后执行）

```bash
SOURCE_COUNT=$(ls sources/xxx/*.md | wc -l)
TARGET_COUNT=$(ls wiki/summaries/*.md | wc -l)
echo "Source: $SOURCE_COUNT, Target: $TARGET_COUNT"
[ "$SOURCE_COUNT" -eq "$TARGET_COUNT" ] || echo "⚠️ 数量不一致！"
```

数量核验失败 → 主会话接管 → 直接处理遗漏文件

### @批量规模适配索引策略（阶段四执行）

| 规模 | 索引策略 |
|------|----------|
| < 20 条 | 逐条列出 |
| ≥ 20 条 | **类目概述 + 目录 glob 引用**，避免 index.md 臃肿 |

## 常见错误警示

| 错误 | 后果 | 防范 |
|------|------|------|
| 省略第三档量刑 | 法律分析不完整 | 处理前先数有几档 |
| 整文件处理（不做分层） | 产出空洞框架 | 按处理单元逐条/逐案/逐节提取 |
| 生成占位符内容 | wiki 质量下降 | 永远只输出实际内容 |
| Agent 报告不可信 | 报告完成但实际遗漏 | 每批完成后立即用脚本验证 |
| 输出 < 500 字符未报警 | 内容空洞被放行 | 低于阈值必须立即复核 |
| 批量变更后未 commit | 大量变更遗留 | 批量删除/变更后立即 commit |
| 删除源文件 | 源资料灭失，不可逆 | **绝对禁止删除 sources/ 下任何文件** |
| ingest 后不建立链接 | wiki 页面孤立 | ingest 同时必须添加 wikilink |
| qmd embed 前未下载模型 | 进程卡在下载步骤 | 先 HF_ENDPOINT=... qmd embed 下载模型 |
| 跨批不完成阶段三/四 | 整合入库不完整 | 每批必须完成该批的阶段三+四 |
| qmd embed 等于整合入库 | 遗漏交叉链接等 | 整合入库 = 6步骤，不能用 embed 代替 |
| **编造法律条文内容** | 严重错误，误导用户 | **涉及数额/日期/适用范围等法条内容必须引用原文，不确定时主动向用户核验，严禁主观推测** |
| 法律条文对比未读原文 | 错误理解法律效力 | 涉及多部法律/解释比较时，必须先读取原文再下结论 |
